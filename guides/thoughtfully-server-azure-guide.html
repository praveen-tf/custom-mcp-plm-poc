Where this sits

The original production plan

Spec 002 is the first production deploy design: a two-app Entra OAuth flow with manually-pasted connector fields, targeting ChatGPT Enterprise. Its auth approach was later superseded by specs 004/005 — a single Entra app behind a FastMCP AzureProvider proxy that ChatGPT Business discovers automatically. What carried forward unchanged is the topology: Container Apps + VNet + Key Vault, and the server itself (spec 001).

02 · Spec 001 · functionality

Two ways to ask

The model reaches data through two whitelist-bound paths. Open-query is the primary mode; templates are a small curated set of blessed queries.

D2 · primary

Open query

The model writes its own SQL. Every statement is parsed to a Postgres AST with pglast and rejected unless it's a single read-only SELECT over whitelisted tables and columns — no SELECT *, no stacked statements, no DML/DDL. A LIMIT is injected automatically.

query("SELECT code, fob_calc FROM styles
       WHERE collection = 'ALICE…'")  → validated → rows
D3 · curated

Parameterized templates

Blessed queries live in policy.yaml. The server generates one typed MCP tool per template, so the model only fills in parameters — values are bound by psycopg, never concatenated into SQL.

get_style_by_code(code="AW-71001-001-001")
list_styles_in_collection(collection="…", limit=50)

The five tools the server advertises — click to expand. The whitelist hides every _airbyte_* and jsonb column, so they never appear in the schema the model sees.

05 · Spec 002 · the handshake

Two-app Entra OAuth

The server never holds a client secret — it only validates tokens. Identity is split across two app registrations.

App A · the API

Resource server

Defines the audience and the pg.read scope via Expose-an-API (api://<appA-client-id>). Manifest requestedAccessTokenVersion = 2 forces v2.0 tokens. The server validates against this — and holds no secret.

App B · the client

What ChatGPT logs in as

Holds a client secret and delegated pg.read with admin consent granted. ChatGPT uses App B's client id + secret to run the auth-code + PKCE flow.

Contrast with specs 004/005: this is two apps + manual OAuth-field paste for ChatGPT Enterprise. Specs 004/005 collapse it to one app behind an AzureProvider proxy that ChatGPT Business discovers (DCR/CIMD) — no fields to paste, and the server mints its own JWT.

07 · Day-two

Operate & verify

Confirm auth is enforced and tokens are shaped correctly. The single most common failure is a v1 token — watch for it.

Auth is enforced
$ curl -i https://<APP_HOST>/mcp/
No token must return 401; the Container App log stream shows OAuth enabled.
Decode the token
▸ paste the access token at jwt.ms
iss = the v2 issuer URL, aud = api://<appA-client-id>, scp contains pg.read.
#1 gotcha — v1 token → 401
! iss == https://sts.windows.net/<tenant>/
If iss is sts.windows.net, you missed App A manifest requestedAccessTokenVersion = 2. Set it, re-mint, retry.
Per-request validation
▸ Container App → Log stream
Each tool call logs a successful token validation; results return to ChatGPT.
Database role
$ psql -d <DB> -c "\dp"
Shows column-level SELECT only (no table-level grant); writes fail as mcp_readonly.
Sensitive column stays hidden
▸ list_accessible_tables() · describe_table()
The spec-001 sensitive column is absent from the advertised schema and unreachable via every tool.
Enterprise connector is immutable enough to plan for: changing the server URL or OAuth config means recreating the connector. And the connector URL is https://<APP_HOST>/mcp/ — the trailing slash matters.
